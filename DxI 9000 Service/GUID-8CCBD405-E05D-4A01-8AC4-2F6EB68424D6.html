Software 1.22 Known Bugs and Behaviors

A list of known bugs or behaviors and countermeasures for recovery for system software version 1.22.

  • Bug/Behavior: Summary of the software bug or system behavior.
  • Details: Explanation of the bug/behavior and how it may impact the system/user.
  • Countermeasure: If applicable, countermeasure to resolve the condition inflicted by the bug/behavior.
Bug/Behavior Details Countermeasure
When Logged In as LabUser, Some Overlays in Machine Control May Be Improperly Displayed with Red Text The Machine Control application contains a view of installed overlays, and is supposed to show unreleased overlays in a red color to warn service if the system is out of configuration. When logged into the LabUser account, some valid overlays will be erroneously shown in red. They are displayed correctly in the Administrator Account. Machine Control application is hidden by default unless enabled by a service engineer. No impact. No countermeasure.
An incorrect reagent serial number may be associated with calibration orders When you order a calibration from the reagent details screen and review it on the calibration order details view it appears that it will run on the specific pack. In fact, the system will only honor the lot, not the serial number. They system may run the curve on any available pack of that lot. No impact. No countermeasure.
Error Handling Events Do Not Match Instrument Status Red system events from some errors state that "The analyzer cannot process samples.", but for error handling conditions where the recovery is successful, the instrument returns to a running state and will accept new samples, but the red system event isn't dismissed. No impact. No countermeasure.
Semi-Quantitative and Quantitative QC mean calculation is incorrect when units are changed The QC statistics values will not be calculated correctly if the data points use different units. No impact. No countermeasure.
Default Save Directory Errors When Exporting Data Files When there are errors trying to export data for offline review to the pre-configured export destination the messages reported to the user are unhelpful in resolving the issue. No impact. No countermeasure.
Shared Reagent Assays Do Not Display Consistent Reagent Test Count Details In 'Test Availability' Message The assays which share the same reagent package and calibration curve (like RBC/Folate) are not holding the same reagent test count in 'Test Availability [7703]' message that sends as part of dynamic interface communication logs when instrument is connected to automation lane. For instruments connected to DxA automation systems, this can affect tube route planning efficacy for tests which share the same reagent and the same curve (mainly RBC/Fol). Samples would need to be manually loaded on the SPU if they are not being routed to the system.
LIS code and Test Code Mismatch Causes Test to not Show on Enhanced Test Order Screen If LIS code is configured to be different from default test code, Enhanced Test Order screen will not display the test. No impact. No countermeasure. This screen is for internal users only. Customers are not directed to use this screen.
Disposed Sample Vessel Incorrectly Referenced During Reserve Volume SV Sample Completion Time Setting In scenario where Reserve Volume is enabled and sample aliquot conditions result in Reserve Volume being fully in its own vessel (no reserve volume in the primary vessel) the Reserve Vessel may get kept onboard for up to 3 hours until the storage time limit is reached. This may result in extra sample vessels being kept longer than the system requires. No impact. No countermeasure.
Results Stuck in Transmitting State if LIS Configuration is Changed or Software is Restarted While they are Waiting to Send Some results in the "Transmitting" state may not get transmitted if the LIS Configuration is changed or the software is restarted. When this happens, then only 10-20 samples are transmitted when the LIS connection is re-established. The rest stay in the "Transmitting" state. There are only two types of results transmission scenarios where this is occurring: * The results were reruns * The results were requested for re-transmission by clicking the "Resend to LIS" button on the result review page This scenario would likely only occur if the LIS connection is being setup for the first time or the lab is experiencing LIS connectivity issues that requires a configuration change or a software restart. To recover and have the remaining transmitted, either the LIS Configuration can be changed again or the console software can be restarted again and the next approximately 10 samples will be sent. Repeat this process until all samples are sent.
Calibration Auto Order Placed for MeMed Child Assays with Active Curve from Edit Order Screen When reagent lots are loaded for all MeMed child assays and calibrated with an active curve, then new reagent lot is loaded only for one of the tests, e.g. the CRP child assay, an auto order is placed for the newly loaded lot. However, after navigating back to the Edit Order screen, snoozing the order, and then unsnoozing it, calibration orders are placed for the other two child assays, Trail and IP10, which already have active curves, along with the newly loaded CRP reagent lot. This only applies to the MeMed assay due to it's unique design. The system could over-use calibrator and reagents since technically only one of the calibrations due and this will re-calibrate all constituents.
Calibration Time Until Due Incorrectly Displayed as N/A When an assay has a valid calibration and a new calibration is run, the Calibration Time Until Due is Incorrectly Displayed as "N/A" instead of the "Days" or "Hours" left on the valid calibration. This occurs on the Calibration Impact tiles on the user interface in the Calibration Due Now -> All Calibrations Page. The remaining calibration time for the valid calibration is not shown while the new calibration is in progress. Users can see the actual calibration curve expiration date by selecting the "Details" view from the "All Calibrations" page.
Hourly cyclic interval of QC not work after you changing from 24 to 8 and change back to 24 again before expected due time Hourly cyclic interval of QC does not auto order at daily start time, after user changing from 24 to 8 and change back to 24 again before expected due time. In an unlikely scenario where the user changes the QC auto due frequency multiple times before the daily start time, the QC becomes auto due at incorrect time (there is no issue in the frequency only issue with the due time). Work around: Once the user changes the frequency before the daily start time, they can let the assay to be auto ordered and post that only change the frequency. No impact. No countermeasure.
Lumi LED Voltage Search for RLU Targets (Stitching RLUs) Failed but No Message to Retry LED Voltage Search and Reschedule LumiDrift An unexpected failure mode was found on an internal instrument and prevented the Luminometer drift check diagnostic from completing. Due to the unexpected failure, the performance of the instrument was not verified. However, the failure was not correctly handled and the instrument continued to run samples without fully notifying the user of the problem. The instrument ran samples with a luminometer calibration that was not verified to be within the expected performance range. No countermeasure.
RSU package download hangs due to intermittent connection Field Service may have to manually correct the installation process after the Remote Software Package fails to download. No impact. Currently installations are only performed by field service.
Substrate Unload Workflow Error when Unloading Both Bottles An unexpected error was reported to the user when attempting to unload both bottles of substrate without a replacement. The user was able to restore instrument operation with basic troubleshooting and loading new bottles of substrate. User can recover by either restarting software or pausing and unpausing system.
System Initialize Race Condition Leaves Instrument in Paused Mode - Trouble Shooting Wizard(s) There is a small opportunity for the system to become stuck in a paused state while a troubleshooting wizard workflow is in progress. The user should avoid pushing the buttons in rapid succession if possible. If this occurs, the user will need to restart the system.
Patient Sample Loaded and not Processed for Non-Barcoded Samples In rare cases, the test order for a non-barcoded tube may not be processed when loaded even though there is a pending manual order. No sample will be aspirated and the order will remain pending. User will be confused why the sample was not processed. To correct, the user can re-present the sample.
Sample Event Page Stops Displaying Events When the Active Sample Event Records Exceed 30MB If there is an extremely high number of sample events, on the order of tens of thousands, there is a potential for the sample events screen to stop showing events. There are no known occurrences of this problem on any real DxI 9000 system. Is not expected to impact performance. No scenarios have been identified in which the DxI 9000 has the potential to generate enough sample events to encounter this problem.
System Allows Initiation of Previous Version Updates Through RSU DxI 9000 software allows the user to initiate an RSU (Remote Software Update) installation that is for a previous version of the system software. For example, if the system is on version 1.22, it is possible to initiate the update that is intended to update the system to 1.20. This could occur if the USB drive that contains the new version also has previous versions of software on it, for example. The installation of the previous version of software would fail if attempted. No impact. No countermeasure.
Tests Can Become Stuck in Progress if LIS Sends Test Orders Using Multiple "O" Order Records If the LIS sends a host-query response for a sample that contains multiple order records, a software deadlock can occur that results in the sample remaining stuck in progress. The tests will eventually be cancelled after the 5-hour limit expires. This does not affect Remisol-connected systems, as Remisol always communicates multiple test requests within a single order record. As a workaround, if possible the customer LIS should be configured to send multiple orders within a single order record. Samples can be stuck in progress for up to 5 hours and flagged NRT. As a workaround, if possible, the customer LIS should be configured to send multiple orders within a single order record.
Calibration Orders Screen Showing Orders for Inactive Calibration Lots When a new pack lot is loaded, the system may automatically order calibrations for other lots in addition to the new one. The user can de-select the extra orders in the calibration ordering screen when they assign calibrator rack IDs to the order. No impact. The customer may modify the auto-ordered calibrations.
Old Completed QC Sample Stuck in Result Processing Step, Delaying the Processing of New Results The control test result may remain in running status after the projected completion time, not reporting results until minutes later. While this test result is being processed, other new results (patients, controls, calibrators) may also have prolonged processing time. User is unable to immediately review test results until the prolonged processing is completed.
Substrate Loader Mechanical Initialize Timeout System initialization could fail if the system is unable to retrieve supply information from the database within a time limit. This has only been observed in software automated testing, and is unlikely to occur on real systems. User may need to repeat initialization.
Disabled Pipettors Prevent Probe Cleaning and Test Scheduling If pipettors have been disabled by service and support, probe cleaning cannot occur and new tests will not start and there is not a clear indication on the user interface why that is the case. No countermeasure. Users are directed in the IFU to use this screen only under supervision of technical support.
Calibration Orders from Reagent Lot Details are For Specific Reagent Serial Number Instead of Only Just Lot When ordering a calibration from the Reagent Lot Details page, the calibration request should be created for the lot of the pack selected by the user. Currently it is also tying that request to a specific pack serial number. That should not be the case on the DxI 9000 as there is no way to ensure sufficient reagent will be available when the request is processed and that can result in the calibration request not being able to be fulfilled. No countermeasure. This does not interfere with the user's ability to calibrate following instructions in the IFU.
Events Show Incorrect Reagent Pack Position After Barcode Reading Failure When an issue occurs loading a reagent pack, an event is created and the position is shown on screen to facilitate troubleshooting. The slot number displayed is off-by-one. They are labeled 1-4 but software considers these positions 0-3. As a work around, the user can identify problem pack by loading them one at a time.
SPU Auto-Recovery: Critical Event and Red Light Bar Remain On After a successful SPU auto-recovery from an error, the system status will remain red until the user initializes the system. No countermeasure.
'Time Remaining' Display Issue At The Bottom Of The Screen For 'Lumi Drift' diagnostics No 'Time Remaining' is shown in the user interface task bar for 'Lumi Drift' diagnostic. It may be hard to predict for the user when the instrument will be available again for normal use. No countermeasure.
Unintended Multiple Aliquots for Tests in Pending State When Rack is Represented The system incorrectly performs duplicate aliquots when a previously introduced sample is re-presented while its associated tests remain in the 'Queued' state. In this scenario, Falcon's logic misinterprets the re-presentation as a need for additional sample volume, leading to redundant aliquoting. This behavior deviates from the expected single-aliquot process and contrasts with the correct handling of re-presented samples when tests are in the 'Scheduled' state, where no further aliquoting occurs. The system may aliquot more sample than is required. No workaround is needed; tests will be run normally.
Tests not started and Samples not Loaded with no Indication Why After an error, the system may require an additional initialization if the pick and place recovery is only partially successful. No countermeasure.
If Reflex and Rerun Rule are Both Triggered, Only One Is Ordered Successfully When multiple rule actions are configured for the same rule condition for example: * If the test is A, Rerun A. * If the test is A, Reflex B. And when a calculated test is configured (the calculated test expression should contain the tests that are being ordered as part of the rule actions) for example: CalTest = A+B Then sometimes due to a race condition, the rule action to create the reflex test may fail. As a workaround, user can create a single rule that reflexes test A & test B to achieve the same outcome. For example: If the test is A, reflex A & Reflex B with suppress checkbox uncheck. Rerun and Reflex actions should not be used together in the same rule. As a work-around, only use the Reflex rule action with the Suppress option disabled if both Rerun and Reflex tests are needed for a single rule.
